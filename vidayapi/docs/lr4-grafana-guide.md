# Grafana: нагрузочное тестирование vidayapi

Сценарии разведены по двум доскам, чтобы auth и public не смешивались на одной оси X:

| Сценарий | Дашборд |
|---|---|
| `WORKLOAD=auth` (матрикс: login → … → unfollow) | <http://localhost:3000/d/loadtest-lr4-auth> |
| `WORKLOAD=public` (feed → video_detail → live_streams) | <http://localhost:3000/d/loadtest-lr4-public> |

Обе доски используют `admin`/`admin`. Workload зафиксирован в SQL каждой доски:
в списке прогонов, деталях сценария и Live-метриках видны только прогоны этого
workload. Ссылки для перехода между досками — в верхнем меню Grafana.

## 1. Переключатели сверху

| Переключатель | Поведение |
|---|---|
| **Тип прогона** | `ramp` / `stress` / `soak` / `soak-errors` / `smoke`. Список берётся из БД, поэтому показывает только те типы, которые реально есть у этого workload |
| **Прогон** | Конкретный `run_id` выбранного типа; отсортирован от новых к старым |

Тумблеров сравнения, фазы, операции и перцентилей больше нет: все графики
показывают **весь прогон** и **агрегат по всем операциям**. Это убирает ситуацию,
когда половина панелей пуста из-за фильтра, не относящегося к выбранному сценарию.
Перцентили на временных рядах фиксированы: p50, p95, p99; в таблицах есть полный
набор p50/p75/p90/p95/p99/p99.7.

«Тип прогона» фильтрует не только список прогонов, но и адаптивную таблицу деталей.
Все остальные графики общие: VU/RPS, задержки, отказы, CDF, ресурсы, JVM и операции
нужны любому сценарию.

## 2. Live: запуск при открытой Grafana

Секция **LIVE** стоит первой и читает Prometheus, а не PostgreSQL. Она **не зависит
от выбранного прогона**:

- `LIVE: текущий прогон` — таблица `viday_loadtest_info`: run_id, CPU, RAM, корутины,
  потоки. Если ничего не запущено, панель показывает `No data` — это нормально.
- `LIVE: RPS и VU` — фактический поток запросов и запланированные VU.
- `LIVE: p95/p99` — перцентили по гистограмме генератора.
- `LIVE: отказы/с` — `unexpected` / `injected` / `business`.
- `LIVE: CPU API`, `LIVE: RAM API` — exporter контейнеров, % от лимита и MiB.
- `LIVE: JVM heap`, `LIVE: HTTP RPS и 5xx/с` — Actuator приложения.

Все live-запросы фильтруются по «активному прогону»:
`last_over_time(viday_loadtest_info{workload="..."}[1m])`. Поэтому старые `run_id`
из retention не засоряют график, а новый прогон появляется автоматически в течение
одного scrape-интервала (5 с) и обновляется каждые 10 с.

Порядок работы:

1. Откройте доску нужного workload.
2. Запустите сценарий: `./scripts/run-loadtest.sh ...` (см. `lr4-loadtest-configuration.md`).
   Для демонстрации падения сервиса под рампом есть готовый запуск
   `make loadtest-fail` (auth, 1 CPU, 256 MiB, 100 корутин, early stop).
3. Не трогайте «Прогон»: LIVE-панели сами покажут текущий run_id и метрики.
4. После завершения прогон импортируется в PostgreSQL и появится в списке «Прогон»
   при сдвиге таймпикера или перезагрузке страницы. Полная история — на SQL-панелях.

## 3. Главные графики

- **VU и RPS во времени** — две оси на одном полотне. По нему видно, как рост VU
  перестаёт давать прирост RPS, а затем начинаются отказы.
- **Перцентили p50/p95/p99 во времени** — log-шкала, чтобы медиана и хвост читались
  одновременно.
- **Отказы, инъекции и бизнес-4xx** — три вида ошибок раздельно.
- **Доля отказов в 5-с окне, %** — порог 95% подсвечен красным. Несколько подряд
  полных окон выше порога — criterion ранней остановки.
- **Накопленные успешные операции и отказы** — наглядно показывает момент падения.
- **Пик отказов**, **5-с окон с откзами ≥95%**, **первый таймстемп окна с перевесом
  отказов** — быстрые KPI катастрофы.

## 4. Детали сценария (адаптивно)

Одна таблица, содержимое которой зависит от типа выбранного прогона:

- **ramp** — ступени из `lt_ramp_curve`: VU, запросы, RPS, p95/p99, отказы,
  стабильность. Кривая «VU → RPS/задержка/ошибки» видна как таблица ступеней,
  а динамика — на общем графике VU/RPS.
- **stress / soak / soak-errors / smoke** — фазы из `lt_phases`: requests, RPS,
  p50/p95/p99, отказы, **время восстановления**. Для ramp колонка восстановления
  содержит `—`, потому что у ramp нет фазы recovery.

Поэтому таблица всегда заполнена и не зависит от того, какой тип прогона выбран.

## 5. Остальные панели

- **CDF во времени** — доля запросов ≤ порога (10…10000 мс) по 5-с окнам.
- **Гистограмма во времени** — heatmap «время × задержка», цвет — число запросов.
- **Операции** — сводка по операциям и топ-15 по p95.
- **Ресурсы контейнеров** — CPU/RAM/диск/сеть по компонентам.
- **JVM** — heap, GC, HikariCP, HTTP RPS/5xx, потоки, Tomcat-сессии.
- **Ресурсы min/max/median** — сводка за прогон и по фазам.
- **Конфигурация, окружение, выводы** — `metadata.config`, `metadata.environment`,
  автоматические findings.

## 6. Время и выбор прогона

Все SQL-ряды построены по реальным таймстемпам (`bucket_ts` / `ts`) и фильтруются
таймпикером. По умолчанию открываются последние 24 часа — так удобнее смотреть live.
Старые прогоны:

1. нажмите «Весь архив (90 дней)»;
2. найдите run в таблице «Прогоны в базе»;
3. кликните по `run_id` — откроется этот же дашборд с таймпикером ровно на интервале
   прогона.

Это важно для коротких smoke/early-stopped прогонов: на широкой оси они выглядят
как один пиксель.

## 7. Проверка

```bash
make loadtest-dashboard   # генерирует обе доски и импортирует их в Grafana

# все SQL-панели через тот же Grafana API, что и дашборд
python3 scripts/probe-grafana-panels.py lr4-v2-matrix-c1-r1024-co300 ramp auth
python3 scripts/probe-grafana-panels.py lr4-good-c1-r256-h64-stress stress auth
python3 scripts/test-dashboard-queries.py          # ramp + stress в benchmark-db
```

Для непустого прогона `No data`, ошибка SQL или пустой ресурсный/JVM график —
дефект, а не ожидаемое поведение. Исключение — LIVE-панели, когда ни один прогон
сейчас не идёт.

## 8. Память: почему не 64 MiB

`APP_RAM_MB=64` и `128` не запускают Spring Boot: контейнер убивается OOM
(`OOMKilled=true`, exit 137) ещё до healthcheck. Практический минимум — `256 MiB`
(heap 128), рекомендуется `512 MiB` (heap 256) для сравнения CPU и стабильных
нагрузочных прогонов. Скрипт `run-loadtest.sh` теперь проверяет это до сборки и
объясняет ошибку. Подробности — в
[lr4-loadtest-configuration.md](lr4-loadtest-configuration.md).
