# Лабораторная работа № 4 — нагрузочное тестирование backend `vidayapi`

> Проект: **vidayapi** (Kotlin/JVM 17, Spring Boot 4.0.5, PostgreSQL, Redis, MinIO).
>
> Задание ЛР4: провести нагрузочное тестирование бэкенда по пользовательским сценариям,
> найти зону отказа и стабильную зону (ramp), проверить поведение под перегрузом и
> время восстановления (stress), провести длительную стабильную нагрузку (soak),
> отдельно — soak с **ровно 10 %** и **20 %** ошибочных операций. Собрать статистику
> задержек (p50/p75/p90/p95/p99/p99.7), RPS (не только средний), распределения,
> гистограммы, временные ряды и ресурсы по компонентам (CPU, RAM, диск, сеть) в
> формате min/max/median, с JSON-иерархией, графиками и Prometheus.
>
> В исходной серии `lr4-final-*` инструмент нагрузки — **k6 0.54.0**. В актуальной версии
> стенда по умолчанию используется собственный генератор на **корутинах Kotlin** с
> настраиваемым диспетчером; `GENERATOR=k6` сохранён для воспроизведения исходной серии.
> Оба генератора пишут совместимый NDJSON, который обрабатывает собственный
> Python-анализатор. Каждый прогон выполняется в отдельном Docker-образе приложения и
> генератора, на **чистом томе PostgreSQL** с детерминированным сидом и одинаковым warmup.
>
> **Настройка CPU × RAM × корутин, ранняя остановка и результаты новых прогонов:**
> [lr4-loadtest-configuration.md](lr4-loadtest-configuration.md).
>
> **Отчёт и все графики — в Grafana:**
> [auth (матрикс)](http://localhost:3000/d/loadtest-lr4-auth) ·
> [public](http://localhost:3000/d/loadtest-lr4-public)
> (admin/admin). Дашборд ЛР3 сохранён отдельно: <http://localhost:3000/d/benchmark-lr3>.

## 0. Результат (TL;DR)

Серия из шести прогонов (`lr4-final-*`) на детерминированном сиде (200 пользователей,
1000 видео, 100 плейлистов), отдельный Docker-образ приложения и генератора на каждый
прогон, чистый том PostgreSQL, warmup 45 с, cpuset-изоляция CPU:

- **Ramp (0→450 VU, 12 мин):** стабильная зона — до **50 VU** (p95 269 мс, ~230 RPS),
  первая нестабильная ступень — 60 VU (p95 555 мс). Отказов (5xx/timeout) **0** за весь
  прогон: деградация выражается в задержке, а не в ошибках. Бутылочное горлышко — CPU API
  (2 ядра), в первую очередь BCrypt-логин.
- **Stress (50→400→50 VU):** под перегрузом p95 вырос с 328 мс до **5.0 с**, RPS — лишь
  с 207 до 248 (насыщение). **Время восстановления — 10 с** (p95 вернулся к 209 мс).
- **Soak (60 VU, 20 мин):** 287 640 запросов, средний RPS 240, **0 отказов**, RPS и
  p50 стабильны во времени; JVM heap стабилен (median 169 MiB), рост working set —
  native/page cache, а не утечка Java-объектов.
- **Soak с ровно 10 % ошибок:** 181 110 запросов, **18 111 инъекций (10.00 %)**, 0
  реальных отказов; p95 826 мс.
- **Soak с ровно 20 % ошибок:** 145 830 запросов, **29 166 инъекций (20.00 %)**, 0
  реальных отказов; p95 1310 мс. Суммарная скорость BCrypt-проверок (~24–25/с) не
  меняется между 0/10/20 % — это потолок CPU, поэтому «полезный» RPS падает
  пропорционально доле инъекций (240 → 201.5 → 162.3 RPS).
- **Grafana:** все результаты — в двух досках (по 81 панели), разделённых по сценарию:
  [auth (матрикс)](http://localhost:3000/d/loadtest-lr4-auth) и
  [public](http://localhost:3000/d/loadtest-lr4-public) (admin/admin).

Каждый прогон — отдельный compose-проект `viday-lt-<run-id>` в сети `viday_loadtest_net`.
Целевое приложение и генератор нагрузки не делят CPU; мониторинг вынесен на отдельные
ядра. Стенд мониторинга (`Grafana + Prometheus + exporter + benchmark-db`) общий и
поднимается один раз, но его CPU- и memory-лимиты зафиксированы.

### 2.1. Компоненты и ограничения

| Компонент | Образ | CPU (cpuset) | Память | Роль |
|---|---|---|---:|---|
| `api-lt` | `viday-loadtest-app:<run-id>` | `2,3` (2 ядра) | 1536 MiB | целевое приложение |
| `postgres-lt` | `viday-postgres-test:local` (PostgreSQL 15) | `4,5` (2 ядра) | 768 MiB | БД, чистый том на прогон |
| `redis-lt` | `redis:7-alpine` | `6` | 160 MiB | кэш |
| `minio-lt` | `bitnamilegacy/minio` | `6` | 256 MiB | S3-совместимое хранилище |
| `k6` | `viday-loadtest-k6:<run-id>` | `8,9` (2 ядра) | 1024 MiB | генератор нагрузки |
| `loadtest-exporter` | `viday-loadtest-exporter:local` | `10` | 128 MiB | Docker-ресурсы → Prometheus/JSONL |
| `prometheus` | `prom/prometheus:v2.55.1` | `10` | 384 MiB | метрики, 7 дней retention |
| `grafana` | `grafana/grafana:11.4.0` | `11` | 384 MiB | дашборды ЛР3/ЛР4 |
| `benchmark-db` | `postgres:15-alpine` | `10` | 384 MiB | PostgreSQL для отчётов ЛР3/ЛР4 |

Ядра `0,1,7` оставлены операционной системе и рабочему окружению. Таким образом,
генератор (`8,9`), целевое приложение (`2,3`), БД (`4,5`) и мониторинг (`10,11`) не
конкурируют за CPU. Внутри мониторинга Prometheus/exporter/benchmark-db делят ядро 10 —
это не влияет на измерения целевого приложения, но отмечено в ограничениях (§11).

### 2.2. Сеть и тома

- `loadtest` — внутренняя bridge-сеть конкретного прогона: k6 → API → PostgreSQL/Redis/MinIO.
- `viday_loadtest_net` — внешняя сеть, через которую Prometheus достаёт `api-lt:8080`
  и exporter; API подключён к обеим сетям.
- `postgres_lt_data` — **новый том на каждый прогон**; после прогона удаляется
  (`docker compose down -v`), поэтому следующий прогон снова получает чистую БД и
  детерминированный сид.
- Результаты k6 монтируются в `loadtest/results/<run-id>/`; контейнер k6 работает
  под uid 12345, каталог заранее получает `chmod 0777`.

### 2.3. Детерминированный сид

Сид выполняется один раз при инициализации чистого тома
(`docker/loadtest/db/99_loadtest_seed.sql`):

| Сущность | Количество | Детали |
|---|---:|---|
| Креаторы | 20 | `loadcreator1..20`, id 1..20, роль 3 |
| Пользователи | 200 | `loaduser1..200`, id 21..220, роль 2 |
| Пароль | — | `VidayLoadTest!42` (BCrypt, cost 10) |
| Видео | 1000 | публичные, id 1..1000, по 20 на креатора |
| Плейлисты | 100 | публичные, id 1..100, по 5 видео |
| Подписки | — | стартовые подписки пользователей на креаторов |

Сид намеренно **не использует случайные значения**: одинаковые id, одинаковое
распределение владельцев и одинаковый объём данных во всех прогонах. Это важно для
сопоставимости кэша, планов запросов и эффектов БД.

## 3. Пользовательский сценарий

Сценарий находится в `loadtest/scenario.js` и одинаков для всех профилей. Одна
итерация — это **сессия пользователя из 10 операций** (при `ERROR_RATE=0`):

| # | Операция (`operation`) | HTTP-запрос | Авторизация | Ожидаемый статус | Смысл |
|---:|---|---|---|---|---|
| 1 | `login` | `POST /api/auth/login` | — | 200 | вход пользователя |
| 2 | `feed` | `GET /api/videos?page=0&size=20` | — | 200 | лента видео |
| 3 | `video_detail` | `GET /api/videos/{id}` | — | 200 | карточка видео |
| 4 | `playlist_detail` | `GET /api/playlists/{id}` | JWT | 200 | публичный плейлист |
| 5 | `available_playlists` | `GET /api/playlists/available` | JWT | 200 | доступные плейлисты |
| 6 | `create_playlist` | `POST /api/playlists` | JWT | 201 | создание плейлиста |
| 7 | `add_content` | `POST /api/playlists/{id}/contents` | JWT | 200/201 | добавление видео |
| 8 | `delete_playlist` | `DELETE /api/playlists/{id}` | JWT | 204 | удаление плейлиста |
| 9 | `follow` | `POST /api/users/{id}/follow` | JWT | 200/409 | подписка (409 — уже подписан) |
| 10 | `unfollow` | `DELETE /api/users/{id}/follow` | JWT | 200/204 | отписка |

После каждой сессии выполняется **think time** `sleep(random(1000..2500) мс)` —
имитация времени, которое пользователь тратит на просмотр/обдумывание. Без think time
k6 выдавал бы неестественно высокий RPS и не отражал бы пользовательскую нагрузку.
Пользователь выбирается детерминированно из 200 сидовых аккаунтов по `__VU` и `__ITER`,
видео/плейлист/креатор — из известных id сида. Логин выполняется в начале каждой
сессии, поэтому JWT не переиспользуется между итерациями.

### 3.1. Почему плейлисты берутся по id 1..100

`GET /api/playlists` в текущей реализации ожидает числовой username из JWT и для
сидовых имён `loaduserN` возвращает 401. Чтобы сценарий не зависел от этой особенности
и оставался детерминированным, публичные плейлисты берутся по известным id из сида
(1..100), а `GET /api/playlists/{id}` вызывается с JWT. Это не меняет профиль нагрузки:
операция чтения плейлиста остаётся в сессии.

### 3.2. Инъекции ошибок (10 % и 20 %)

В тестах ошибок сессия состоит ровно из 10 операций, но часть нормальных операций
заменяется **намеренно ошибочными**:

| Режим | Нормальных | Ошибочных | Всего | Доля ошибок |
|---|---:|---:|---:|---:|
| `soak` | 10 | 0 | 10 | 0 % |
| `soak-errors` `ERROR_RATE=0.1` | 9 | 1 | 10 | **10 %** |
| `soak-errors` `ERROR_RATE=0.2` | 8 | 2 | 10 | **20 %** |

Типы ошибочных операций (циклически, детерминированно по seed):

| Тип | Запрос | Ожидаемый статус |
|---|---|---|
| `error_invalid_login` | `POST /api/auth/login` с неверным паролем | 401 |
| `error_unauthorized_playlist` | `POST /api/playlists` без JWT | 403 |
| `error_invalid_playlist` | `POST /api/playlists` с пустым именем | 400 |
| `error_not_found_user` | `GET /api/users/99999999` | 404 |

> **Почему нет `GET /api/videos/99999999`?** В текущей реализации отсутствующее
> видео приводит к `EmptyResultDataAccessException` и **HTTP 500**. Это реальный
> баг API; если включить его в инъекции, «10 % ошибок» дадут 2 % настоящих 5xx и
> смешают намеренные 4xx с отказом backend. Поэтому тип исключён из error-soak;
> баг зафиксирован в §11 и рекомендуется к исправлению отдельно.

4xx от инъекций — **ожидаемый результат**, а не отказ. В отчёте они учитываются
отдельно (`errors_injected`), чтобы не смешивать намеренные ошибки с реальными
5xx/timeout. `http.expectedStatuses(200, 201, 204, 400, 401, 403, 404, 409)`
не даёт k6 пометить их как `http_req_failed`.

## 4. Профили нагрузки

Все официальные прогоны серии `lr4-final-*` используют один и тот же сценарий,
одинаковый warmup 45 с, одинаковые образы и одинаковый сид. Меняется только профиль.

| Профиль | k6 executor | Длительность | Нагрузка | Что проверяет |
|---|---|---|---:|---|
| `smoke` | `constant-vus` | 35 с | 2 VU | корректность сценария/сида, отсутствие 5xx |
| `ramp` | `ramping-vus` | 12 мин | 0 → 450 VU, 10 ступеней + 2 мин на 450 | зона стабильности и точка деградации |
| `stress` | 3 × `constant-vus` | 12 мин | 50 VU (3 мин) → 400 VU (4 мин) → 50 VU (5 мин) | перегруз, деградация, восстановление |
| `soak` | `constant-vus` | 20 мин | 60 VU | длительная стабильность, тренд RAM/CPU |
| `soak-10pct` | `constant-vus` | 15 мин | 60 VU, 10 % ошибок | влияние ошибок на задержки/ресурсы |
| `soak-20pct` | `constant-vus` | 15 мин | 60 VU, 20 % ошибок | влияние ошибок на задержки/ресурсы |

### 4.1. Ramp: точные ступени

| Минута | Целевое число VU |
|---:|---:|
| 0–1 | 10 |
| 1–2 | 25 |
| 2–3 | 50 |
| 3–4 | 75 |
| 4–5 | 100 |
| 5–6 | 150 |
| 6–7 | 200 |
| 7–8 | 275 |
| 8–9 | 350 |
| 9–10 | 450 |
| 10–12 | 450 (плато) |

Ramp не «ломает» приложение мгновенно: ступени по 1 минуте дают прогреться кэшам,
пулам соединений и JIT, а плато на максимуме показывает установившееся поведение.
Критерий стабильной ступени в анализе: **p95 < 500 мс и доля 5xx/timeout < 1 %**.

### 4.2. Stress: фазы

| Фаза | Время | VU | Назначение |
|---|---|---|---|
| `baseline` | 0–3 мин | 50 | эталонная p95 для расчёта восстановления |
| `overload` | 3–7 мин | 400 | перегруз, рост очередей и tail latency |
| `recovery` | 7–12 мин | 50 | возврат к baseline после снятия перегруза |

Восстановление считается не «на глаз», а по правилу: берётся p95 последних 60 с
baseline, порог = `max(1.5 × baseline_p95, baseline_p95 + 20 мс)`; затем recovery
разбивается на 10-секундные окна, и первое окно, в котором p95 ≤ порога и ошибки < 1 %
**два окна подряд**, считается моментом восстановления. Время — от старта фазы
`recovery` до этого окна.

## 5. Методика измерений и статистика

### 5.1. Сбор сырых данных

k6 запускается с `--out json=raw.json`; каждая точка — NDJSON-объект:

```json
{"type":"Point","metric":"http_req_duration","data":{
  "time":"2026-11-05T00:52:48.123456Z","value":123.45,
  "tags":{"scenario":"ramp","phase":"ramp","operation":"feed","status":"200"}}}
```

В анализ попадают только `http_req_duration` с тегом `operation` — то есть только
запросы пользовательского сценария. Служебные запросы `setup()` (проверка ленты) и
healthcheck приложения не входят в статистику. Для каждой точки сохраняются:
время, длительность, сценарий, фаза, операция, HTTP-статус, признаки
`unexpected`/`business`/`injected`.

### 5.2. Перцентили и распределения

- Перцентили считаются по **всем сырым точкам** прогона, а не по средним значениям:
  `p(q) = sorted[floor((n−1)q)]` с линейной интерполяцией между соседними рангами.
- Обязательный набор: **p50, p75, p90, p95, p99, p99.7**. p99.7 нужен, чтобы увидеть
  поведение «худших 0,3 %» — именно там проявляются GC-паузы, блокировки БД и
  насыщение пула Tomcat.
- **CDF** строится по 102 точкам (0, 0.01, …, 1.0 + 0.999): по оси X — задержка в мс,
  по оси Y — доля запросов, уложившихся в эту задержку. CDF показывает форму
  распределения, а не только одну цифру.
- **Гистограмма** — 30 бинов от 0 до p99.9; последний бин включает хвост. По ней видно
  модальность и «толщину» хвоста.
- Среднее и стандартное отклонение сохраняются, но **не используются как единственная
  характеристика**: при тяжёлом хвосте среднее вводит в заблуждение, поэтому в отчёте
  всегда есть медиана и перцентили.

### 5.3. RPS: не только средний

Для каждой фазы и операции считаются:

- средний RPS = `requests / duration_s`;
- **медиана RPS** по 5-секундным интервалам;
- **min** и **max** RPS по 5-секундным интервалам;
- временной ряд RPS с шагом 5 с (для графиков).

Это позволяет отличить «стабильные 200 RPS» от «150 RPS с провалами до 40 и всплесками
до 400». В Grafana панель RPS показывает одновременно ряд, VU и таблицу
среднее/медиана/min/max по фазам.

### 5.4. Изоляция CPU

| Что | Ядра | Почему |
|---|---|---|
| API | 2,3 | целевое приложение не должно делить ядра с генератором |
| PostgreSQL | 4,5 | БД — второй по важности ресурс |
| Redis + MinIO | 6 | вспомогательные сервисы, низкая нагрузка |
| k6 | 8,9 | генератор не должен «съедать» CPU приложения |
| Prometheus + exporter + benchmark-db | 10 | сбор метрик не влияет на API |
| Grafana | 11 | UI/запросы дашборда отдельно |
| ОС и рабочее окружение | 0,1,7 | остаётся хосту |

Дополнительно контейнер k6 ограничен `--cpus=2 --memory=1g`, API — `mem_limit: 1536m`,
PostgreSQL — `768m`. Это фиксирует не только ядра, но и верхнюю границу памяти.

### 5.5. Ресурсы: что и как собирается

Собственный exporter (`docker/loadtest/exporter/exporter.py`) опрашивает Docker Engine
API и Actuator приложения, пишет Prometheus-метрики и два JSONL-потока:

- `container-samples.jsonl`: CPU, RAM working set, диск, сеть и PID по компонентам;
- `app-samples.jsonl`: JVM heap, GC, HikariCP, HTTP и потоки Tomcat.

**CPU нормализован к эффективному лимиту контейнера: 100% = все доступные ему ядра.**
Учитываются одновременно cpuset, Docker NanoCPUs и cgroup quota. В отчётах также есть
сырое значение Docker, но графики и сводки используют нормализованное. Python считает
`min / max / median / mean` и тренды RAM/CPU.

Скорости диска и сети считаются как приращение счётчика / приращение времени между
соседними сэмплами. Окно анализа — от старта до конца официального прогона ±15 с;
warmup не попадает в отчёт. Номинальный шаг опроса — 5 с, фактическое число сэмплов
указано в отчёте.

Оба JSONL-потока импортируются в PostgreSQL (`lt_resource_samples`, `lt_app_samples`).
Все отчётные графики ресурсов и JVM читают эти таблицы, поэтому не зависят от диапазона
времени и 7-дневного retention Prometheus. Prometheus остаётся источником оперативного
мониторинга, но не единственным хранилищем истории.

### 5.6. Равные условия и воспроизводимость

- На каждый прогон собираются **два образа с уникальными тегами**:
  `viday-loadtest-app:<run-id>` и `viday-loadtest-k6:<run-id>`. Dockerfile и параметры
  сборки не меняются; уникальный тег — доказательство отдельного образа.
- **Чистый том PostgreSQL** на каждый прогон + один и тот же сид. Данные не накапливаются
  между прогонами (плейлисты, подписки, новые пользователи).
- **Одинаковый warmup 45 с** (4 VU, smoke-профиль, не входит в отчёт) до официального
  запуска: JIT, пулы Hikari, кэши Redis, page cache PostgreSQL.
- **Одинаковые JVM-параметры**: `-Xms256m -Xmx768m -XX:+UseG1GC -XX:MaxGCPauseMillis=200`.
- `metadata.json` фиксирует CPU-модель, ядро, версию Docker, cpuset, id образов,
  git-коммит и число грязных файлов, доступную RAM на старте.
- Сырые `raw.json` (сотни МБ) остаются в `loadtest/results/<run-id>/`; компактные
  `report.json`, `report.md`, `resource-summary.json`, `summary.json`, `metadata.json`
  копируются в `docs/lr4-results/<run-id>/`.
- Официальная серия запускается одной командой `RUN_PREFIX=lr4-final ./scripts/run-all-loadtests.sh`;
  каждый профиль можно воспроизвести отдельно (`ONLY=...`).

## 6. Оркестрация прогона

`scripts/run-loadtest.sh` выполняет шаги:

1. проверяет Docker, сеть `viday_loadtest_net`, свободную RAM;
2. поднимает общий мониторинг (Grafana, Prometheus, exporter, benchmark-db);
3. собирает образ приложения и образ k6 с тегом прогона;
4. поднимает `viday-lt-<run-id>` с чистым томом PostgreSQL;
5. ждёт health API (до 300 с);
6. выполняет warmup 45 с;
7. запускает k6 с `--out json` и `--summary-export`;
8. останавливает стенд и удаляет том;
9. считает отчёт (`scripts/analyze-loadtest.py`);
10. копирует компактные отчёты в `docs/lr4-results/<run-id>/`;
11. импортирует `report.json` в PostgreSQL Grafana (`scripts/import-loadtest-to-db.py`);
12. обновляет симлинки `latest`.

`scripts/run-all-loadtests.sh` запускает серию последовательно; каждый профиль —
отдельный вызов оркестратора, поэтому падение одного прогона не смешивает данные
с другим.

### 7.4. Soak с инъекциями ошибок: 10 % и 20 %

Оба прогона — тот же soak (60 VU, 15 мин), но в каждой сессии из 10 операций часть
заменяется намеренно ошибочными (§3.2). Инъекции детерминированы и дают **ровно**

| `lr4-final-soak-20pct` | 8 / 2 | 145 830 | 29 166 | **20.00 %** | 162.3 | 159.4 / 94.6 / 199.2 | 0 | 0 | 36.3 | 63.6 | 850.2 | 1 310.3 | 1 745.2 | 1 889.8 |

**Инъекции по типам (прогон 20 %):** `error_invalid_login` — 7 296,
`error_unauthorized_playlist` — 7 294, `error_not_found_user` — 7 289,
`error_invalid_playlist` — 7 287; все с ожидаемыми статусами 401/403/404/400,
таймаутов 0.

**Ключевые наблюдения:**

- **Реальных отказов нет ни в одном прогоне:** инъекции не «ломают» backend — это
  штатная обработка ошибочных действий пользователя.
- **Бутылочное горлышко — BCrypt-логин.** Суммарная скорость BCrypt-проверок
  (нормальный `login` + `error_invalid_login`) держится на одном уровне во всех трёх
  soak-прогонах: ~24.0/с (0 %), ~25.2/с (10 %), ~24.4/с (20 %). Это потолок CPU на двух
  ядрах, поэтому при добавлении инъекций «полезный» RPS падает пропорционально:
  240.0 → 201.5 → 162.3 RPS.
- **Хвост растёт:** p95 556.8 → 826.4 → 1 310.3 мс; p99.7 1 007 → 1 166 → 1 890 мс.
  Причины: (1) сессия укорачивается и доля дорогих операций (login/BCrypt) на итерацию
  растёт; (2) ошибочный логин — это ещё одна BCrypt-проверка в общей очереди.
- **Ресурсы сопоставимы с чистым soak:** нормализованный CPU API median 100% во всех
  трёх прогонах, RAM API ~519–542 MiB median, PostgreSQL ~4–8% CPU. Откаты транзакций
  (400/401/403/404) дешевле успешных записей, поэтому БД даже свободнее.
- **k6 RAM:** в прогоне 20 % максимум 691 MiB против 1 024 MiB в чистом soak —
  инъекции с фиксированными URL не добавляют кардинальности тегов генератора.

**Вывод:** приложение корректно обрабатывает внештатные действия пользователей:
ровно 10 %/20 % ошибочных операций не приводят к 5xx, таймаутам или деградации
ресурсов; влияние ограничивается ростом хвоста задержки из-за очереди BCrypt.

### 9.2. Переменные

| Переменная | Значение | Использование |
|---|---|---|
| `run` | `run_id` выбранного прогона этого workload | все панели |

| `phase` | `All` или существующая фаза | временные ряды и распределения |
| `operation` | `All` или операция выбранной фазы | все пользовательские метрики |

по реальным таймстемпам и подчиняются таймпикеру Grafana, включая CDF и гистограмму
(`lt_cdf_ts` / `lt_histogram_ts`). Кривая «VU → …» осталась только таблицей ступеней.

Для `All` распределения используют худшую по p95 фазу выбранной операции. Таблица

### 9.4. Как читать

1. Выберите `run` (например, `lr4-final-ramp`) и `phase` (`all`).
2. Сравните p50/p95/p99 на графике «Перцентили задержки во времени» и в таблице
   «Перцентили по фазам».
3. Для ramp откройте ряд «Ramp»: таблица показывает каждую ступень и `стабильно`.
4. Для stress — ряд «Stress»: p95 по фазам и stat «Время восстановления».
5. Для soak — ряд «Ресурсы» и «JVM»: смотрите не только средние, но и тренд RAM,
   CPU, GC и Hikari.
6. Для 10 %/20 % — `run = lr4-final-soak-10pct/20pct`, `phase = all`: колонка
   «инъекции» показывает фактическую долю ошибочных операций.

> **Почему p95 в таблице прогона и на графике могут отличаться?** Таблица
> `lt_scenario_summary` считает перцентиль по всем точкам фазы, а график — по
> 5-секундным окнам и затем берёт максимум окна. Это разные вопросы: «какой p95
> у всех запросов» и «какой худший p95 был в окне». Обе цифры полезны.

## 11. Ограничения и честные оговорки

1. **Стенд — один хост, 12 логических ядер.** cpuset-изоляция не изолирует общий
   L3-кэш, контроллер памяти и дисковую подсистему. При интерпретации абсолютных
   цифр это надо учитывать; относительные сравнения профилей корректны.
2. **API ограничен 2 ядрами и 1.5 GiB.** Это сделано специально, чтобы получить
   насыщение на доступном железе. На другом CPU/лимите граница stable zone будет
   другой; методика и сценарий переносимы, абсолютные RPS — нет.
3. **BCrypt-логин доминирует.** Каждая сессия начинается с проверки пароля
   (BCrypt cost 10), поэтому `login` — самая дорогая операция (p50 0.56 с в soak,
   p95 11 с в overload). Это честный пользовательский сценарий, но он не описывает
   чистое чтение ленты. Для оценки чтения нужен отдельный сценарий без логина.
4. **MinIO не нагружается медиафайлами.** Сценарий работает с метаданными и
   seed-URL; загрузка/транскодирование видео не входит в ЛР4. Поэтому CPU/RAM MinIO
   почти нулевые — это ожидаемо, а не «недогрузка».
5. **k6 и высокая кардинальность URL.** k6 автоматически добавляет тег `url`;
   URL `add_content`/`delete_playlist` содержат уникальный id плейлиста, поэтому
   за 20 минут накопилось **400 010 time series** (предупреждения k6 на 100k/200k/400k).
   Это раздуло RAM генератора до лимита **1 024 MiB** (в soak) и вызвало всплески
   disk write/swap. На результат это не повлияло: k6 CPU median 11 %, ошибок и
   прерванных итераций нет, RPS стабилен. Но для длинных (>30 мин) прогонов нужно
   исключить `url`/`name` из system tags:
   `systemTags: ['status', 'method']` в `options` (или `--system-tags status,method`).
   Официальная серия оставлена с исходным сценарием, чтобы все прогоны были
   сопоставимы; это ограничение генератора, а не API.
6. **Soak 20 минут не доказывает отсутствие медленной утечки.** API working set
   вырос на ~129 MiB (+4.6 MiB/мин), хотя JVM heap стабилен (median 169 MiB).
   Для уверенного вывода нужен 1–4-часовой soak и профилировщик native-памяти.
7. **RPS min/max чувствительны к границам.** В таблицах RPS median/min/max считаются
   по 5-секундным окнам; min включает старт/переходы (например, ramp с 0 VU), max —
   короткие всплески. Для сравнения используйте median и средний RPS, а не min/max
   как SLO.
8. **Восстановление — 10-секундная дискретность.** Алгоритм recovery использует
   окна по 10 с и требует два успешных окна подряд; поэтому «10 с» означает
   «второе окно», а не точность до миллисекунд.
9. **Ошибки 10 %/20 % — это 4xx, а не 5xx.** Инъекции проверяют обработку
   ошибочных пользовательских действий (401/403/404/400), а не отказы backend.
   Реальные 5xx/timeout в серии не появились; это отдельный, более жёсткий сценарий.
10. **Объём сырых результатов.** `raw.json` занимает сотни МБ–1 ГБ на прогон и не
    коммитится в git. Все графики Grafana, включая ресурсы и JVM, хранятся в SQL-таблицах
    `lt_*`; 7-дневный retention Prometheus на сохранённую историю не влияет.

## 12. Как воспроизвести

### 12.1. Требования

- Linux с Docker 24+ и Docker Compose v2;
- минимум 6–8 свободных логических ядер (в работе использованы 0–11);
- ~10 GiB свободной RAM (API 1.5 GiB, PostgreSQL 0.75 GiB, k6 1 GiB, мониторинг ~1 GiB,
  плюс page cache);
- свободные порты 3000 (Grafana), 5434 (benchmark-db), 8080 (API в демо-стенде),
  9090 (Prometheus), 9101 (exporter);
- ~3–5 GiB на диске для сырых результатов серии.

### 12.2. Полная серия

```bash
cd vidayapi

# 1) один раз: Grafana + Prometheus + exporter + benchmark-db
make grafana-up

# 2) полная официальная серия: smoke, ramp, stress, soak, soak-10pct, soak-20pct
RUN_PREFIX=lr4-final WARMUP=45s ./scripts/run-all-loadtests.sh
# или
make loadtest-all

# 3) дашборд (если меняли генератор дашборда)
make loadtest-dashboard
```

Серия идёт последовательно; каждый профиль — отдельный образ приложения, отдельный
образ k6, чистый том PostgreSQL и одинаковый warmup.

### 12.3. Отдельный профиль

```bash
# ramp 0→450 VU
ONLY=ramp RUN_PREFIX=lr4-final ./scripts/run-all-loadtests.sh

# stress 50→400→50

ONLY=soak RUN_PREFIX=lr4-final SOAK_VUS=60 SOAK_DURATION=20m ./scripts/run-all-loadtests.sh

ONLY=soak-20pct RUN_PREFIX=lr4-final SOAK_DURATION=15m ./scripts/run-all-loadtests.sh
```

Или напрямую:

SCENARIO=soak SOAK_VUS=60 SOAK_DURATION=20m RUN_ID=lr4-final-soak ./scripts/run-loadtest.sh

## 14. Что ещё можно улучшить

1. **Убрать высокую кардинальность k6.** Добавить в `options`:
   ```js
   systemTags: ['status', 'method'],
   ```
   и перезапустить длинные soak. Это уменьшит RAM генератора в разы и уберёт
   предупреждения о 400k time series. На результаты API это не влияет, но делает
   стенд чище.
2. **Увеличить длительность soak** до 1–4 часов и снимать `jvm_memory_used_bytes`
   после GC, `jvm_gc_live_data_size_bytes`, native memory (NMT). Текущие 20 минут
   показывают стабильный heap, но не дают права утверждать «утечек нет».
3. **Добавить сценарий без логина** (чистое чтение ленты/видео), чтобы отделить
   стоимость BCrypt от стоимости чтения. Сейчас логин доминирует и маскирует
   оптимизации чтения.
4. **Проверить горизонтальное масштабирование:** 2 инстанса API за балансировщиком
   на тех же 2+2 ядрах; ожидаемо почти линейный рост RPS при неизменной p95, пока
   PostgreSQL не станет узким местом.
5. **Настроить SLO-алерты** в Grafana: p95 > 500 мс 5 минут, 5xx > 1 %, Hikari
   pending > 0, GC pause > 100 мс/с.
6. **Снять профиль CPU** (async-profiler/JFR) под нагрузкой 60 VU: подтвердить,
   что топ — BCrypt/`login`, а не, например, сериализация или RLS-политики.

## Приложение B. Глоссарий

| Термин | Значение |
|---|---|
| **VU** | virtual user — виртуальный пользователь k6, выполняющий сессию |
| **Think time** | пауза между действиями пользователя (в работе 1–2.5 с) |
| **RPS** | requests per second — запросы в секунду |
| **p95** | 95-й перцентиль: 95 % запросов быстрее этого значения |
| **p99.7** | 99.7-й перцентиль: хвост «худших 0.3 %» |
| **CDF** | cumulative distribution function — накопленная функция распределения |
| **Ramp** | постепенный рост нагрузки до отказа/деградации |
| **Stress** | кратковременный перегруз с последующим восстановлением |
| **Soak** | длительная стабильная нагрузка для поиска утечек/деградации |
| **Injected error** | намеренно ошибочная операция (4xx), не считается отказом |
| **Unexpected error** | 5xx, timeout или обрыв — реальный отказ |
| **Stable zone** | ступень ramp с p95 < 500 мс и 5xx < 1 % |
| **Recovery** | возврат p95 к baseline после снятия перегруза |
