# ЛР4: конфигурируемое нагрузочное тестирование

Документ описывает запуск с разными CPU, RAM, корутинами и типом нагрузки. Полная
методика — в [lr4.md](lr4.md), устройство генератора — в
[lr4-architecture-and-running.md](lr4-architecture-and-running.md), панели — в
[lr4-grafana-guide.md](lr4-grafana-guide.md).

## Быстрый запуск

```bash
make grafana-up
make loadtest SCENARIO=smoke WORKLOAD=auth
make loadtest SCENARIO=ramp WORKLOAD=public CPU=1 RAM=512 COROUTINES=200 THREADS=2
make loadtest-fail      # auth, 1 CPU, 256 MiB, 100 корутин: ramp до падения
```

Grafana: <http://localhost:3000/d/loadtest-lr4-auth> (auth/матрикс) и
<http://localhost:3000/d/loadtest-lr4-public> (public), `admin`/`admin`. CPU и RAM применяются
к контейнеру API через Docker Compose, а не зашиваются в образ. Для каждого прогона
создаются уникальные теги образов, чистый Compose-проект и новый том PostgreSQL.
Прогоны внутри матрицы выполняются последовательно и не конкурируют друг с другом.

## Параметры Makefile

| Параметр | По умолчанию | Назначение |
|---|---:|---|
| `SCENARIO` | `smoke` | `smoke`, `ramp`, `stress`, `soak`, `soak-errors` |
| `WORKLOAD` | `auth` | `auth`: login и защищённые операции; `public`: только публичные GET без BCrypt |
| `GENERATOR` | `coroutines` | собственный Kotlin-генератор; `k6` оставлен для auth-совместимости |
| `CPU` | `2` | лимит ядер API; автоматически выделяется отдельный cpuset |
| `RAM` | `1536` | лимит памяти API, MiB; минимум `256`, рекомендуется `512+` |
| `APP_HEAP_MB` | `RAM / 2` | максимальный Java heap; минимум `64`, вне heap нужно ≥ `128` MiB |
| `APP_XMS_MB` | `heap / 2` | начальный Java heap |
| `COROUTINES` | `450` | число рабочих корутин и верхний предел VU |
| `THREADS` | `4` | потоки собственного диспетчера корутин |
| `ERROR_RATE` | `0` | доля намеренных 4xx в auth: `0`, `0.1`, `0.2` |
| `REQUEST_TIMEOUT` | `30s` | таймаут одного HTTP-запроса |
| `WARMUP` | `45s` | прогрев перед официальным прогоном; `0` отключает |
| `RAMP_MAX_VUS` | `450` | целевой максимум ramp, фактически ограничен `COROUTINES` |
| `RAMP_STEP_DURATION` | `1m` | длительность каждой ступени ramp |
| `RAMP_PLATEAU_DURATION` | `2m` | финальное плато ramp |
| `SOAK_VUS` / `SOAK_DURATION` | `60` / `20m` | параметры стабильной нагрузки |
| `EARLY_STOP` | `1` | включить детектор критического отказа |
| `EARLY_STOP_AFTER` | `30s` | минимальная длительность до остановки |
| `FAILURE_WINDOW` | `5s` | размер полного окна детектора |
| `FAILURE_WINDOWS` | `3` | требуемое число смежных окон |
| `FAILURE_MIN_REQUESTS` | `20` | минимум завершённых запросов в каждом окне |
| `FAILURE_THRESHOLD` | `0.95` | минимальная доля 5xx/timeout/обрывов в каждом окне |

Длительности задаются суффиксом `s`, `m` или `h`. `WORKLOAD=public` поддерживается
только собственным генератором и требует `ERROR_RATE=0`: неверные сочетания отклоняются
до запуска. k6 всегда выполняет login и поэтому не выдаётся за public-нагрузку.

### Минимум RAM для API

Spring Boot 4 + JVM не помещаются в контейнер на 64 или 128 MiB: процесс убивается
OOM (`OOMKilled=true`, exit 137) ещё до healthcheck. `run-loadtest.sh` проверяет это
до сборки и запуска:

- `RAM ≥ 256` MiB;
- `APP_HEAP_MB ≥ 64` MiB;
- вне heap остаётся ≥ 128 MiB (metaspace, code cache, стеки, direct buffers).

При `RAM < 384` выводится предупреждение: это минимальный режим, под нагрузкой возможен
OOM. Для сравнения CPU используйте `RAM=512` (heap 256) или больше. При OOM скрипт
показывает `docker inspect` с `OOMKilled` и подсказывает, что увеличить.
Например, ошибочный запуск `CPU=1 RAM=64` теперь завершается сразу с кодом 2 и
объяснением, а не ждёт 300 секунд unhealthy-контейнера.

## Два сценария нагрузки

`WORKLOAD=auth` сохраняет исходную последовательность: login, feed, video detail,
плейлисты, follow/unfollow и намеренные 4xx при соответствующем `ERROR_RATE`.

`WORKLOAD=public` выполняет три публичных запроса: `feed`, `video_detail`,
`live_streams`. Это отдельный способ измерения без стоимости BCrypt, а не фильтр отчёта:
фильтр `feed` в Grafana только скрывает login из выбранной панели, но не убирает его
фактическую нагрузку на CPU.

Короткий ramp без логина:

```bash
make loadtest SCENARIO=ramp WORKLOAD=public CPU=1 RAM=512 \
  COROUTINES=300 THREADS=2 RAMP_MAX_VUS=300 \
  RAMP_STEP_DURATION=5s RAMP_PLATEAU_DURATION=20s \
  REQUEST_TIMEOUT=2s WARMUP=5s THINK_MIN_MS=50 THINK_MAX_MS=100
```

### Ремп «до падения» сервиса

`COROUTINES` — это и есть число VU: генератор не поднимет больше пользователей,
чем рабочих корутин. Поэтому при `COROUTINES=100` бесполезно ставить
`RAMP_MAX_VUS=300` — план будет обрезан до 100 VU (в текущей версии с
предупреждением в логе). Для чистого «сервис упал под рампом» есть готовая цель:

```bash
make loadtest-fail
```

Она запускает auth-сценарий (login + запись), 1 CPU, минимальные 256 MiB
(heap 64), 100 корутин, ramp 10→25→50→75→100 VU по 5 с и плато 20 с. На 1 CPU
auth ломается уже на 40–50 VU: время ответа уходит за `REQUEST_TIMEOUT=2s`,
появляются timeout/5xx, и после 3 смежных 5-секундных окон с ≥95% отказов
генератор останавливается сам (`early_stopped=true`).

Почему не `WORKLOAD=public`: публичные чтения на 1 CPU держат ~1000–1100 RPS
при p95 ~100 мс и 0 отказов даже при 100% CPU. Замкнутый контур из 100
корутин не создаёт очередь в 2 секунды, поэтому сервис не падает. Это не
баг детектора, а физика нагрузки: чтобы получить отказ, нужен более тяжёлый
auth-профиль (BCrypt + запись) либо больше корутин.

## Матрица CPU × RAM × корутин

```bash
RUN_PREFIX=lr4-v2-matrix \
RAMP_MAX_VUS=300 RAMP_STEP_DURATION=5s RAMP_PLATEAU_DURATION=20s \
WARMUP=5s REQUEST_TIMEOUT=2s THREADS=2 THINK_MIN_MS=50 THINK_MAX_MS=100 \
make loadtest-matrix CPUS="1 2" RAMS="512 1024" \
  COROUTINES="100 300" SCENARIO=ramp WORKLOAD=auth
```

Выполняется декартово произведение значений. Каждый элемент получает `run_id` вида
`<prefix>-c<cpu>-r<ram>-co<coroutines>`; `RUN_PREFIX`, `THREADS`, timeout, критерий
остановки и длительности пробрасываются в каждый прогон. Для public-матрицы замените
`WORKLOAD=auth` на `WORKLOAD=public`.

## Ранняя остановка упавшего сервера

По умолчанию `EARLY_STOP=1`. Неожиданным отказом считаются HTTP 5xx, таймаут или обрыв
соединения; ожидаемые намеренные 4xx не участвуют. Остановка происходит только когда:

1. с начала прогона прошло не меньше `EARLY_STOP_AFTER=30s`;
2. есть три **смежных полных** окна по 5 секунд;
3. в каждом окне завершилось минимум 20 запросов;
4. доля неожиданных отказов в каждом окне не ниже 95%.

Таким образом, успехов не более 5%, а отказов минимум в 19 раз больше успешных операций.
Пустое окно само по себе не считается доказательством отказа. Обычно критический прогон
останавливается примерно через минуту, а не продолжает 12-минутный план. Причина
сохраняется в `run-state.json`, `metadata.config` и Grafana, статус — `early_stopped`.
Для диагностики без остановки используйте `EARLY_STOP=0`.

## Сохранение истории

Для `<run-id>` создаются:

- `loadtest/results/<run-id>/raw.json` — все исходные точки;
- `report.json`, `report.md`, `resource-summary.json`, `metadata.json`, `summary.json`;
- компактная копия отчётов в `docs/lr4-results/<run-id>/`;
- строки во всех таблицах `lt_*` PostgreSQL Grafana.

Повторный импорт одного `run_id` идемпотентен, разные прогоны не перезаписывают друг
друга. История находится в Docker-томе `bench_postgres_data`; не удаляйте его, если она
нужна. Контейнерные ресурсы и Actuator-снимки JVM/HTTP/потоков сохраняются в PostgreSQL,
поэтому 7-дневный retention Prometheus не удаляет графики старых прогонов.

## Переключатели Grafana

Сценарий задан доской: `loadtest-lr4-auth` или `loadtest-lr4-public`. На каждой доске
видны только прогоны её workload.

- **Тип прогона** — `ramp` / `stress` / `soak` / `soak-errors` / `smoke`; список берётся
  из БД, поэтому показывает только реально выполненные типы этого workload.
- **Прогон** — выбранный `run_id` этого типа, список от новых к старым.

Других фильтров нет: все графики показывают весь прогон и агрегат по всем операциям,
перцентили зафиксированы (p50/p95/p99 на временных рядах, полный набор в таблицах).
Поэтому панели не пустеют из-за фильтра «не из этого сценария».

Секция **LIVE** читает Prometheus и не зависит от выбранного прогона: запустите тест
при открытой Grafana, и RPS, VU, p95/p99, отказы, CPU/RAM, JVM heap и HTTP 5xx появятся
в течение 10 с. Запросы LIVE отфильтрованы по активному прогону
(`last_over_time(viday_loadtest_info[1m])`), поэтому старые `run_id` не засоряют график.

Все временные ряды используют реальные таймстемпы и подчиняются таймпикеру Grafana
(по умолчанию последние 24 часа; «Весь архив» — 90 дней). CDF и гистограмма раскладываются
по 5-секундным окнам и тоже следуют таймпикеру. Детали сценария — одна адаптивная
таблица: ramp → ступени `lt_ramp_curve`, stress/soak → фазы `lt_phases` и время
восстановления.

Графики успеха/отказов показывают весь прогон: темп в каждом 5-секундном окне и
накопленные значения. Отдельные таблицы структурируют CPU/RAM/heap, корутины и потоки.
CPU нормализован: 100% — все доступные контейнеру ядра.

## Актуальная матрица `lr4-v2-matrix`

Восемь auth-ramp прогонов выполнены последовательно на Ryzen 5 6600HS, двумя потоками
диспетчера, `RAMP_MAX_VUS=300`, ступенями 5 с, плато 20 с, warmup 5 с,
timeout 2 с, think time 50–100 мс. Во всех случаях сработал строгий критерий 95%;
длительность — именно время нагрузки, без сборки образов и запуска стенда.

| CPU | RAM, MiB | Корутины | Длит., с | Запросы | RPS | p95, мс | Отказы за прогон | CPU max | Статус |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 1 | 512 | 100 | 30,8 | 1 416 | 45,9 | 2 001,8 | 48,45% | 100% | `early_stopped` |
| 1 | 512 | 300 | 34,4 | 1 876 | 54,5 | 2 001,8 | 57,36% | 100% | `early_stopped` |
| 1 | 1024 | 100 | 36,7 | 1 892 | 51,5 | 2 001,5 | 50,37% | 100% | `early_stopped` |
| 1 | 1024 | 300 | 34,8 | 1 949 | 56,0 | 2 002,0 | 55,36% | 100% | `early_stopped` |
| 2 | 512 | 100 | 63,3 | 8 229 | 130,0 | 2 000,7 | 13,37% | 100% | `early_stopped` |
| 2 | 512 | 300 | 49,1 | 7 013 | 142,7 | 2 001,1 | 33,40% | 100% | `early_stopped` |
| 2 | 1024 | 100 | 49,1 | 5 776 | 117,5 | 2 000,9 | 17,97% | 100% | `early_stopped` |
| 2 | 1024 | 300 | 43,6 | 5 518 | 126,5 | 2 001,3 | 34,58% | 100% | `early_stopped` |

Процент отказов за весь прогон включает начальные работоспособные окна. Критерий
остановки проверяет отдельно последние три полных окна: в каждом не менее 20 запросов
и не менее 95% отказов. p95 около 2 секунд соответствует заданному request timeout.
В каждом отчёте сохранено 5–10 Actuator-снимков; панели JVM, HTTP и потоков заполнены.
Это один короткий прогон на конфигурацию, а не статистическая оценка влияния RAM: для
выводов об устойчивых различиях нужны повторные прогоны с одинаковыми параметрами.

Полные отчёты: `docs/lr4-results/lr4-v2-matrix-c<cpu>-r<ram>-co<coroutines>/`.
Для всех восьми конфигураций SQL-проверка `ramp/login + p50/p95/p99.7` вернула
`проблемных панелей: 0`.

## Проверка без длительной нагрузки

```bash
./gradlew :loadtest:test --no-daemon --console=plain
python3 -m py_compile docker/loadtest/exporter/exporter.py \
  scripts/analyze-loadtest.py scripts/import-loadtest-to-db.py \
  scripts/generate-loadtest-dashboard.py scripts/probe-grafana-panels.py
bash -n scripts/run-loadtest.sh scripts/run-loadtest-matrix.sh
make loadtest-dashboard
python3 scripts/probe-grafana-panels.py lr4-final-stress stress auth
python3 scripts/probe-grafana-panels.py lr4-v2-smoke-public smoke public
```

SQL-проверка должна завершиться строкой `проблемных панелей: 0`.
