# Шпаргалка к ЛР3: что происходит и как читать графики микробенчмарка

> Это **теория-пояснение** к лабораторной работе №3 на примере модуля
> `benchmark/` проекта vidayapi. Цель — чтобы вы на защите уверенно объяснили:
> **что** мы замеряем, **как** устроен замер, **почему** мы его так обезопасили
> и **что именно показывает каждый график** в отчёте
> (`benchmark/build/reports/benchmark/official/` и `docs/lr3-charts/official/`).
>
> Рядом лежит отчёт с цифрами: [`docs/lr3.md`](lr3.md). Здесь — не отчёт, а
> «разжёвывание»: читайте медленно, мысленно открывайте графики и сверяйтесь с числами.

---

## 1. Сначала: что вообще у нас замеряется

По заданию нужно сравнить **два разных объекта**. Мы выбрали **две библиотеки,
решающие одну и ту же задачу** (пункт 1 задания):

| | **Jackson 3** (объект A) | **kotlinx.serialization** (объект B) |
|---|---|---|
| Что это | `tools.jackson` + `jackson-module-kotlin` | официальный Kotlin-плагин сериализации |
| Как находит поля | **в рантайме, через рефлексию** (Kotlin reflection) | **на этапе компиляции** (генерирует `serializer()` под каждый класс) |
| В проекте | используется в production (Spring Boot сериализует ответы) | не используется (кандидат на замену) |

**Задача одна**: взять DTO «видео» (`BenchmarkPayload`: id, title, tags[], stats{}, variants[])
и
1. **чтение** — из JSON-строки построить объект (разбор текста: токены → поля → объекты);
2. **запись** — из объекта получить JSON-строку (обход полей → экранирование → буфер);
3. **смешанный сценарий** — делать то и другое одновременно в двух потоках.

> Простая ментальная модель: **чтение = парсинг текста, запись = печать текста.**
> Это одни из самых частых операций любого API — поэтому их и сравнивают.

## 2. Почему «просто замерить время» недостаточно (физика микробенчмаркинга)

Хотим измерить операцию, которая занимает **~1–5 микросекунд** (µs). Проблемы:

| Помеха | Что происходит | Как боремся |
|---|---|---|
| `System.nanoTime()` стоит ~20–30 нс | если мерить 1 операцию, погрешность = 1–3 %… а при 100 нс-операции таймер > 20 % | **батчи**: замеряем по 256 операций и делим на 256 → цена таймера ~0,1 нс/операция |
| JIT-компилятор (C1, C2) | первые тысячи вызовов медленные (интерпретация → компиляция) | фаза **warmup** |
| GC (сборщик мусора) | раз в некоторое время пауза — операция «вдруг» стала в 10 раз дольше | много сэмплов + смотрим **перцентили**, а не только среднее |
| Ленивая инициализация библиотеки | первый `readValue` у Jackson грузит десерриализаторы | warmup перед замером |
| Другие процессы / турбо-буст CPU | шум на соседних ядрах, частота плавает | **1 ядро** (`--cpuset-cpus=0`), docker-изоляция |
| JIT «выкидывает» неиспользуемый результат | если мы НЕ используем результат операции, компилятор удалит сами вычисления (dead-code elimination) и покажет фантастические 0 нс | **Blackhole** «съедает» результат |

**Вывод**: один замер ничего не значит. Нужны (а) тысячи повторений, (б) отбрасывание
прогревочных, (в) статистика распределения, (г) изоляция окружения. Именно это и делает
наш харнесс.

## 3. Как устроен один «сэмпл» в нашем бенчмарке

```
sample = {
  t0 = System.nanoTime()
  повторить batch=256 раз: { blackhole.consume( operation() ) }
  t1 = System.nanoTime()
  latency_операции = (t1 - t0) / 256   // нс на ОДНУ операцию
}
```

- **batch** — сколько операций «упаковать» в один замер. Чем больше, тем меньше
  доля таймера, но тем хуже видно отдельные медленные операции (они усредняются
  внутри сэмпла). 256 — разумный компромисс.
- **Blackhole** — контейнер, который запоминает `identityHashCode` результата.
  Так JIT не может решить, что результат не нужен, и убрать вычисления.
- Фаз три (по Требованию 2 задания):
  - **warmup** (2000 сэмплов = 512 000 операций) — прогреваем JIT, кэши, инициализацию библиотек; **в статистику не идёт**;
  - **measure** (1000 сэмплов = 256 000 операций) — **только отсюда** считается статистика (это и есть «не менее 100 испытаний», Требование 1);
  - **teardown** (250 сэмплов = 64 000 операций) — «дожариваем» и считаем, что работа завершилась корректно; **в статистику не идёт**, но количество операций честно записывается в отчёт (Требование 8f).

> Переменные: `--samples`, `--warmup`, `--teardown`, `--batch`, `--mixed-pairs`
> (или переменные окружения `BENCH_*`).

### А что с overhead нашего инструмента?

Overhead (Требование 7) = стоимость самого инструмента на одну операцию:
`(2×nanoTime + цикл + Blackhole) / batch`. В прогоне `official` он получился
**4,42 нс/операция** — это меньше половины цены одного `nanoTime()` и целевых
«4–5 нс» из задания. Если бы мы мерили по одной операции, overhead был бы 40–60 нс —
больше, чем наш замер в 1,3 µs имеет право ошибаться. Поэтому **батчи — это
не просто удобство, а математически необходимая техника**.

## 4. Таблица чисел: mean / стdev / min / max / перцентили

Для каждого кейса (`read/write/mixed × jackson/kotlinx`) отчёт печатает таблицу.
Что означают колонки (на примере `read.jackson` → `official`):

| Метрика | Значение | Смысл |
|---|---|---|
| mean | 4 504,9 нс | **среднее арифметическое** по 1000 сэмплов. Чувствительно к выбросам |
| stdev | 337,3 нс | стандартное отклонение: «типичный» разброс вокруг среднего |
| min | 4 345,1 нс | самая быстрая операция (нижний физический предел на этом CPU) |
| max | 12 934,1 нс | самая медленная (GC-пауза, планировщик ОС и т.п.) |
| **p50** | **4 446,6 нс** | **медиана**: ровно половина операций быстрее этого значения. Главная метрика |
| p75 | 4 486,7 нс | 75 % запросов уложились в это время |
| p90 | 4 565,2 нс | 90 % запросов — в это время |
| p95 | 4 787,4 нс | 95 % |
| p99 | 5 468,2 нс | 99 % — **самый важный «хвостовой» перцентиль для сервисов** |

**Почему медиана, а не среднее?** Среднее «портится» редкими выбросами: один
замер в 12 934 нс из 1000 почти не сдвигает медиану, но заметно тянет mean вверх.
Для ответа «как быстро эта операция обычно выполняется» медиана честнее;
для ответа «какая наихудшая задержка, которую увидит пользователь» нужен **p99**.

**Как читать «p99 = 5 468 нс»**: если API сделает 100 000 таких операций,
примерно 99 000 уложатся в 5,5 µs, а ~1000 будут медленнее (иногда на порядок).
В сервисной разработке хвост (tail latency) — это то, что реально чувствует
пользователь: «средняя» может быть отличной, но p99 — валится.

## 5. График №1 — временной ряд (Требование 8a)

Файл: `charts/read.jackson-timeseries.svg` (и у каждого кейса свой).

```
ось X = номер сэмпла (0…999)   → порядок ВО ВРЕМЕНИ
ось Y = latency, нс/операция
```

**Как читать:**

1. **Где «полоса» точек** — почти все 1000 точек лежат в узкой горизонтальной
   полосе: это «обычная» стоимость операции. У `read.jackson` полоса ~4 300–4 600 нс.
2. **Всплески вверх** — редкие выбросы (5–13 µs) — это GC-паузы или планировщик ОС.
   Важно: они не случайны «всегда», они происходят редко — и именно из-за них p99
   (5 468 нс) заметно выше p50 (4 447 нс).
3. **Минимум полосы** = min (4 345 нс) — сколько физически стоит операция в идеале
   (когда ничего не помешало).
4. Пунктирные линии: min / p50 / p99 / max — быстрый визуальный ориентир.
   На нашем графике они подписаны справа.

**Что этот график ДАЁТ**: показывает **стабильность во времени**. Если бы полоса
«плыла» вверх — это был бы эффект деградации (утечка памяти, нагрев, замедление
частоты CPU). Если бы полоса была «рваной» — нестабильность окружения. У нас полоса
ровная — замер стабилен, выбросы дискретны.

**Сравнение двух библиотек**: откройте рядом `read.jackson-timeseries.svg` и
`read.kotlinx-timeseries.svg`. У kotlinx полоса лежит **ниже** (~2 480–2 700 нс),
то есть на диаграмме её «облако точек» заметно ниже облака Jackson. Расстояние
между облаками — это и есть выигрыш ~42 %.

## 6. График №2 — CDF: распределение по перцентилям (Требование 8b)

Файл: `charts/read.jackson-cdf.svg`.

CDF (cumulative distribution function) — **функция распределения**:

```
ось X = латентность, нс/операция
ось Y = доля запросов (0 … 1, показано в %), которые УЛОЖИЛИСЬ в эту латентность
```

Точка на кривой `(x, y)` читается так: **«y% запросов выполнились не медленнее x нс»**.

**Как читать (по шагам):**

1. Возьмите точку `X = 4 500 нс` на графике `read.jackson` → пересечение с кривой
   даёт ~0,55 → **~55 % запросов уложились в 4,5 µs**.
2. Чтобы найти p50: проведите **горизонтальную линию из Y = 0,5** до пересечения
   с кривой, затем вертикально вниз на ось X → получите **4 447 нс** = медиана.
3. Аналогично p95: линия из Y = 0,95 → X ≈ 4 787 нс. На наших графиках перцентили
   p50/p75/p90/p95/p99 нарисованы вертикальными пунктирами с подписями.

**Свойства CDF, которые полезно знать:**

- Кривая всегда **монотонно растёт** от 0 до 1 (не может «убывать»).
- **Чем левее кривая — тем быстрее** операция (при том же Y координата X меньше).
- **Крутой участок** = большинство запросов скучены в узком диапазоне (стабильно).
- **Длинный «пологий хвост» вправо** = есть редкие, но сильно медленные случаи
  (GC и т.п.). По длине хвоста сразу видно, насколько «грязный» p99.

**Сравнение двух библиотек на CDF** — самый наглядный способ: у `read.kotlinx`
кривая **лежит левее** кривой `read.jackson` на всём протяжении → kotlinx быстрее
**по всем перцентилям**, а не только по среднему. Если бы кривые пересекались —
одна библиотека выигрывала бы у «типичных» значений, другая — в хвосте.

## 7. График №3 — гистограмма (Требование 8c)

Файл: `charts/read.jackson-histogram.svg`.

```
ось X = диапазоны латентности (корзины, 30 шт.)
ось Y = сколько сэмплов попало в каждую корзину
```

Гистограмма отвечает на вопрос: **«как выглядит распределение времени по форме?»**

**Как читать:**

1. **Один высокий узкий столбик** — почти все операции имеют примерно одинаковую
   скорость (нормальная картина для прогретого кода). У `read.jackson` основной
   пик в корзине ~4 300–4 600 нс, и он покрывает почти все 1000 сэмплов.
2. **Справа «мусорный хвост»** из корзин с высотой 1–3 — редкие выбросы
   (GC-паузы). Именно эти столбики портят p99 и max.
3. **Форма**:
   - узкий симметричный пик → детерминированная операция;
   - **бимодальность** (два пика) → «два режима работы»: например, до и после
     GC, или быстрый путь (кэш) и медленный (промах);
   - широкий «размазанный» график → операция нестабильна (аллокации, рефлексия).

**Живой пример из прогона**: у `mixed.jackson` основной пик ~2,7 µs, а хвост
дотягивается до корзины ~22 µs → поэтому p99 = 8,6 µs (в 3× больше медианы).
У `mixed.kotlinx` гистограмма — узкий пик ~2 µs и хвост всего до ~2,7 µs →
p99 = 2,4 µs. **По гистограммам видно не только «быстрее/медленнее», но и
«стабильнее/неровнее».**

## 8. Что мы сравниваем между библиотеками (и что означают «−42 %»)

Отчёт строит пары по сценарию: `jackson` (A) vs `kotlinx` (B) и считает

```
Δ = (B − A) / A × 100 %
```

Отрицательный Δ — **B быстрее**; положительный — **A быстрее**.

Реальные цифры прогона `official` (JVM 17, 1 ядро, Docker):

| Сценарий | A = Jackson (p50) | B = kotlinx (p50) | Δ median | Трактовка |
|---|---|---|---|---|
| чтение | 4 446,6 нс | 2 557,6 нс | **−42,5 %** | kotlinx в ~1,74 раза быстрее |
| запись | 1 275,0 нс | 1 300,3 нс | **+2,0 %** | статистически одинаково (разница меньше шума) |
| смешанный | 2 722,6 нс | 1 985,5 нс | **−27,1 %** | kotlinx быстрее и стабильнее (p99 −72 %) |

**Почему так:**

- **Чтение.** Jackson разбирает JSON через рефлексию (`jackson-module-kotlin`
  обращается к Kotlin-метаданным в рантайме), kotlinx генерирует
  `BenchmarkPayload.serializer()` на этапе компиляции — обычный код без рефлексии.
  Отсюда выигрыш в парсинге.
- **Запись.** Обе библиотеки пишут в буфер сопоставимо быстро; рефлексия меньше
  сказывается «на выходе». Разница 2 % — это шум между прогонами (во 2-м прогоне
  `official-2` kotlinx оказался даже на 5,6 % быстрее) → честный вывод: **паритет**.
- **Смешанный.** Два потока на одном ядре конкурируют; у Jackson аллокации при
  рефлексии чаще «цепляют» GC → жирные хвосты (max 22 µs), у kotlinx — 2,7 µs.

> **Золотое правило чтения дельт**: изменение до ~5 % при таком шуме — это «шум»;
> 27–42 % и тем более разница в p99 на 44–72 % — это реальный, воспроизводимый
> результат (подтверждён вторым прогоном).

## 9. Зачем все предохранители (отвечаем на «а зачем это всё?»)

| Приём | Проблема без него | Что даёт |
|---|---|---|
| **warmup / teardown** (Требование 2) | первые вызовы в 5–20 раз медленнее (JIT + ленивая инициализация) — статистика «врала бы» | измерием **установившийся** режим, операции warmup/teardown отдельно посчитаны в отчёте |
| **1000 испытаний** (Требование 1) | 10 замеров — это случайность | перцентили и медиана становятся достоверными (p99 по 1000 точкам имеет смысл) |
| **1 ядро CPU** (Требование 4) | операции конкурируют с другими потоками/процессами → невоспроизводимо | детерминизм: `Cpus_allowed_list: 0`, `availableProcessors = 1` в отчёте |
| **docker-образ на каждый прогон** (Требование 6) | разные окружения, фоновая нагрузка, отличие версий JRE | одинаковое окружение на каждую попытку; два прогона (`official`, `official-2`) дали ±6 % |
| **overhead 4,4 нс** (Требование 7) | не ясно, насколько инструмент искажает замер | мы знаем: инструмент добавляет 4,4 нс (~0,1 % от 1,3–4,5 µs) и вычитаем его в «net-медианах» |
| **Blackhole** | JIT «съедает» операцию, показывая нереальные 0 нс | результат операции всегда используется |
| **CDF + гистограмма + временной ряд** (Требования 8a–8c) | одно число (mean) скрывает хвосты | видна форма распределения и стабильность |

## 10. Как быстро «освежить» формулы перед защитой

```text
latency (нс/операция)   = время_батча / batch
throughput (оп/сек)     = 1e9 / latency
Δ, %                    = (B − A) / A × 100
net median              = median − overhead          (наш инструмент стоит 4,4 нс)
p99, нс                 = значение, быстрее которого выполняется 99 % операций
```

Сколько операций в прогоне: простые кейсы — 512 000 (warmup) + 256 000 (measure)
+ 64 000 (teardown) = **832 000**; смешанные — вдвое больше (**1 664 000**). Это и
есть ответ на Требование 8f («количество операций за время теста с детализацией»).

## 11. Глоссарий (слова, которые можно услышать на защите)

| Термин | Что значит |
|---|---|
| **Микробенчмарк** | замер быстрых операций (100 нс … 50 мс), а не интегральных сценариев |
| **Latency / задержка** | время одной операции (у нас в наносекундах) |
| **Throughput / пропускная способность** | сколько операций в секунду (у нас 222k–766k оп/с) |
| **Перцентиль p** | граница, ниже которой лежит p×100 % наблюдений |
| **Медиана (p50)** | «середина» — половина быстрее, половина медленнее |
| **Среднее (mean)** | сумма / количество |
| **Стандартное отклонение (stdev)** | средняя «удалённость» наблюдений от среднего |
| **Выброс (outlier)** | точка, сильно отклоняющаяся от основной массы (у нас — GC-паузы) |
| **Хвост распределения** | редкие большие значения справа на гистограмме/CDF |
| **JIT (C1/C2)** | компиляция Java-методов во время работы; «прогрев» — время до их компиляции |
| **GC (SerialGC)** | сборщик мусора; его паузы — главный источник выбросов |
| **Blackhole** | приёмник результатов, не дающий JIT удалить вычисления |
| **Batch-измерение** | N операций за один замер времени, делим на N |
| **Overhead инструмента** | доля измеренного времени, которую вносит сам измеритель |
| **Warmup / teardown** | фазы прогрева и «дожарки», исключаемые из статистики |
| **CPU pinning (cpuset)** | закрепление процесса за конкретным ядром |
| **CDF** | вероятность «время ≤ x» как функция от x |
| **Гистограмма** | сколько наблюдений попало в каждый диапазон значений |
| **Таймсерия** | значение во времени (задержка по номеру испытания) |
| **tail latency (p99)** | наихудшая типичная задержка — то, что видит самый невезучий пользователь |
